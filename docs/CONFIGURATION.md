# Configuration

Configuration is per remote organization. Use the guided setup wizard for a new connection or the organization panels for later changes. Only a Jira administrator can invoke configuration and write resolvers.

## Guided setup

The wizard validates and persists progress in this order:

1. **Remote Jira connection**: name, URL, administrator email, API token, target project.
2. **Source scope**: at least one allowed local project and an optional JQL filter.
3. **Direction**: `push` or `bidirectional`.
4. **Mappings**: users, custom fields, statuses, issue types, and projects.
5. **Features**: comments, links, attachments, replacement, and related options.
6. **Webhook**: remote endpoint instructions and secret state.
7. **Communication preflight**: verifies the remote connection and, for bidirectional mode, recent authenticated webhook receipt.
8. **Initial synchronization**: preview, classify, approve, then start or defer.
9. **Review and activation**: summarizes the effective configuration.

Saving a later step invalidates earlier dependent validation when its inputs change. Re-run preflight after changing credentials, direction, scope, or the remote URL.

## Connection credentials

Each remote organization requires:

- **Remote URL**: an `https://<site>.atlassian.net` Jira Cloud origin.
- **Remote administrator email**: the Atlassian account associated with the API token.
- **Remote API token**: generated by the remote account and entered only through the configuration UI.
- **Target project key**: the remote project used when a project mapping does not specify another target.

API tokens and incoming webhook secrets are stored with Forge secret storage. They are not returned by configuration resolvers, are not written into ordinary organization records, and are redacted from logs and audit records.

An empty token on update means "keep the existing token". Use the explicit token-replacement action when a new token is required. Do not paste tokens into issue descriptions, comments, repository files, or support tickets.

## Allowed projects and JQL

The project allow-list is mandatory for synchronization. An organization with no allowed project is blocked rather than being treated as "all projects".

- Allowed projects are local source project keys.
- The optional JQL filter further restricts outbound sources inside the allowed projects. It applies to every new outbound write, including comments/replies, attachments, links, status transitions and counterpart notices, as well as issue creation/updates. Queued and recovered work rechecks current eligibility at execution time. Both local link endpoints must be selected; a mapping is not continuing export permission.
- Both constraints apply to the local source scope.
- A remote webhook must independently be restricted to the intended remote projects.
- Initial synchronization requires at least one allowed project and validates its project and JQL scope before preview.

An excluded or unverifiable source produces no new outbound write; existing destination content is retained. A deleted/unreadable local issue cannot authorize a remote counterpart notice. Local source JQL is not an inbound destination permission. See [the outbound selection guarantee](PACKAGE1_OUTBOUND_SELECTION_GUARANTEE.md).

JQL is limited to 500 characters by the setup and initial-sync validation. Avoid volatile clauses, such as relative dates, when approving an initial sync because the preview is checksum-bound to the configuration.

## Push versus bidirectional

**Push** is the default. It sends supported local changes to the remote target and never processes remote events.

**Bidirectional** keeps the local-to-remote path and additionally accepts supported remote events through the authenticated Forge web-trigger. It requires:

- an incoming webhook secret
- a remote Jira System Webhook
- communication preflight confirmation
- the remote project scope controlled in the webhook JQL

Changing direction does not generate or rotate a signing secret. Create or rotate it explicitly in bidirectional setup; it is displayed once.

## User mappings

User mappings translate local and remote Jira account IDs for assignee and reporter fields.

- Load local and remote users before adding mappings.
- Unmapped users do not become arbitrary remote accounts. The affected field is skipped or left unassigned according to the field path.
- Automatic matching can reduce manual work but should be reviewed before activation.
- A fallback of `unassigned` is the default.

## Field mappings

Field mappings connect local and remote custom field IDs.

- Only mapped custom fields are copied through this path.
- Load mapping data with the correct local project. Local and remote project keys may differ.
- Jira-rejected or read-only fields are recorded as learned rejections and shown for cleanup.
- System fields such as summary, description, priority, labels, due date, components, versions, and estimates use their built-in paths.

## Status mappings

Status mappings connect local statuses to remote statuses by identifier or name, and are used in reverse for inbound transitions.

- The destination status must be reachable through a transition exposed by the target workflow.
- A missing transition is reported as a transition failure; workflows are not cloned or modified.
- Reverse mappings are used when the remote state must be applied locally.

## Issue-type and project mappings

Issue-type and project mappings control the target issue type and, when configured, the remote project.


## Feature defaults

| Setting | Default | Notes |
| --- | --- | --- |
| `syncComments` | On | Human comments with display-name attribution, verified reply context and duplicate guards |
| `syncLinks` | On | Pending links retained until both issues are mapped |
| `syncAttachments` | Off | Secure attachment transfer when enabled |
| `syncCrossReference` | On | Connector-owned cross-reference in descriptions |
| `recreateDeletedIssues` | Off | Legacy setting; does not enable automatic replacement |
| `automaticReplacementAfterDeletion` | Off | Explicit opt-in for confirmed-deleted counterparts |
| `propagateAttachmentDeletions` | Off | Deletes only explicitly mapped attachments |
| `maxAttachmentSizeBytes` | Jira limits | Optional lower connector limit |

## Attachments

Attachment synchronization uses Jira's attachment metadata and IDs:

- the source attachment must be readable by the source account
- the effective limit is the lower of the two Jira limits and the optional connector limit
- filenames and media types are validated and sanitized
- duplicate prevention uses mapping records and operation ledgers
- a successful upload is mapped to the destination attachment ID
- deletion propagation is off by default and never deletes a Jira issue

Do not enable deletion propagation until attachment mappings have been verified. Use the attachment reconciliation workflow when an upload outcome is ambiguous.

## Webhook configuration

For each bidirectional remote site, configure the existing Jira System Webhook with the credential-free callback URL and separate one-time signing secret generated by SyncApp. Set the Jira Secret field and URL together, and leave Exclude body unchecked. Include only the supported events and restrict its JQL to the remote projects that may send changes.

The endpoint:

- accepts `POST` with `application/json` only
- rejects credentials in query parameters
- validates the organization path and verifies HMAC-SHA256 on the original UTF-8 body before JSON parsing
- rejects payloads above 1 MiB
- records non-sensitive receipt proof for setup diagnostics
- discards events while global pause is active

The callback URL is reusable and retrievable; the signing secret is shown once and never included in configuration exports. Rotation invalidates the old signing key immediately without changing the URL. Old bearer URLs cannot authenticate. Follow the [coordinated cutover runbook](F04-SIGNED-WEBHOOKS.md).

## Initial synchronization configuration

The initial-sync job is bound to the approved preview checksum and configuration checksum. Changes to scope, credentials, target project, mappings, or feature options after preview can invalidate the approval. Re-preview and re-approve rather than overriding a checksum mismatch.

Batch size is 25, with at most five items processed per queue invocation. The processing lease and create ledger prevent duplicate issue creation across retries.

## Recurring reconciliation configuration

| Setting | Default | Range or behavior |
| --- | --- | --- |
| `recurringReconciliationEnabled` | Off | Explicit per-organization opt-in |
| `reconciliationIntervalMinutes` | 60 | 15 minutes to 7 days |
| `reconciliationCommentOnReview` | On | Local marker-tagged review comment |
| `reconciliationFailureThreshold` | 3 | 1 to 20 failed attempts before notification count |

Disabling reconciliation cancels an active run without reversing completed Jira writes. The hourly recovery heartbeat provides the scheduling resolution; no exact-minute guarantee exists.

## Staging preflight configuration

The read-only staging preflight uses its own `STAGING_*` variables and a local
environment file. If the resolved credential file is inside the repository, Git
must ignore it; file mode must be `600`. Reports are restricted to the canonical
private `artifacts/` subtree. See [Staging preflight](STAGING_PREFLIGHT.md) for
the variable list, host allow-list, report location, validation, and exit codes.

- A missing or invalid issue-type mapping blocks a create rather than guessing.
- A project mapping can direct different local projects to different remote projects.
- The target project must be within the configured remote scope.
